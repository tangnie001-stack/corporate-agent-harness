## Context

- **现状**：企微通道（`src/channels/wecom/`，多机器人长连接）只做"入站 @ → 回复"；生成侧复用站点同一条管线（`turn_runner.start_turn` → `agent_service`）。会话按 `uuid5(NS, "wecom|{bot_key}|{group|single}|{id}")` 派生，历史按 `session_id` 存在 Redis（供上下文）与 PostgreSQL（持久）；`start_turn` 会自动幂等建 `sessions` 行，并写入 Redis + `conversation_history`。
- **阿里云侧**：ARMS 告警可通过「通用 Webhook」通知对象外发；载荷为 Alertmanager 风格（顶层 `alerts` 数组、`commonLabels`、`status`），通知策略支持**事件分组**与**未恢复重复通知**；Webhook 通知对象支持**自定义 Header（Header+Param ≤6 个）**与**自定义 body 模板（Go Template，≤500 字符）**；**Webhook 硬超时 5 秒**。
- **已被排除的路**：企微**群机器人**（webhook）是单向的，`mentioned_list` 只能 @ 真人成员，**@ 不到另一个机器人** ⇒ "群机器人 → 智能机器人"这条触达链在机制上不成立。
- **未验证的关键能力**：官方 `aibot` SDK 有 `client.send_message(chatid, body)`（主动发送，不依赖入站帧），但本项目**从未使用**；且它**没有流式与更新语义**（`reply_stream` 的多帧快照、`update_template_card` 都要求入站帧的 `req_id`）。

## Goals / Non-Goals

**Goals:**

- 阿里云告警到达后自动跑一轮 Agent，结论推回值班群
- 与现有企微问答链路彻底隔离，不互相污染
- 最小可用：不挂知识库、不绑定智能体、不做订阅式
- 群侧体验闭环：报警来了有回执，分析挂了也有兜底

**Non-Goals:**

- **订阅式寻址**（在群里 @ 订阅）—— 留 v2
- **MCP 接入**（连阿里云查日志）—— 本 change 不做
- 多群/多业务线路由、报警升级与静默、消息队列与重试
- 隐藏报警会话（靠 `user_id` 不匹配天然不可见即可）

## Decisions

### D1 入口走 ARMS「通用 Webhook」通知对象，而不是 Grafana 直连

保留 ARMS 的事件分组、重复通知、自动恢复与告警历史；且 Grafana 自身的 webhook 载荷不是我们要的形状。

### D2 端点契约：收包即返，不等待分析

ARMS Webhook **硬超时 5 秒**，超时即判发送失败（可能重试）。因此端点在校验 + 去重通过后**立刻返回成功**，把"跑 Agent → 推送"放进后台任务。

**返回码不承载分析结果** —— 分析失败由群消息兜底体现，端点不因分析失败而改变应答。

### D3 鉴权用请求头 token（不放 URL 路径）

**替代方案**：token 放 URL 路径。**弃选理由**：现有中间件会把完整 path 打进日志（`response_processor` 与异常处理器打印 `request.url`），Nginx `access.log` 也记 —— token 是唯一凭据，进日志就等于泄露，而泄露的后果是**有人能往值班群灌假告警**。

ARMS Webhook 通知对象支持自定义 Header ⇒ 用请求头承载 token 可行。

校验用 `hmac.compare_digest`（常数时间）；不匹配返回 **404**（不返回 401/403，不暴露端点存在）。

### D4 告警配置可选，不阻断启动

未配置 token ⇒ 端点**恒 404**（与"不暴露端点存在"一致），应用照常启动。本地/开发环境不必配。

### D5 目标群先写死，订阅式留 v2

**理由**：订阅式比写死多出四样 —— 订阅表、指令解析、退订、以及"群里谁能订阅"。而**两种方式的第一步完全相同**（都得先在群里 @ 一次拿到 `chatid`），所以先写死不白做。

配置沿用 `WECOM_BOTS` 同款的**单行 JSON**（留多群余地），由配置模块在启动期校验。

### D6 报警单开会话（`scope=alert`），不复用群会话

**理由**：① 报警与群聊天的语义无关，混在一起会污染群历史并长期占用上下文；② 复用会与"正在进行的群对话"抢**同一会话的并发闸门**，报警可能被 `TurnBusy` 拒掉 —— 而故障时恰恰最容易有人在群里排查。

**代价（已接受）**：群里追问"刚才那个报警"时接不上上下文。

### D7 会话 key 取报警自带标识，去重用告警指纹

- **`alarmId`**（原始告警 ID）→ 派生报警会话标识
- **`alerts[].fingerprint`** → 入口去重键。官方文档明确"**同一组标签的告警其指纹相同**"，即对同一问题重复触发保持恒定

**`alarmId` 的稳定性待实测**：若同一条告警重复通知时 `alarmId` 变化，则每次重复都会新开会话并重跑 Agent（成本与刷屏）；若恒定，则"相同报警标识归入同一会话"成立且天然去重。实测前该条按"由报警自带标识派生"实现，不承诺恒定。

### D8 入口去重：逐条 fingerprint + 时间窗

载荷顶层 `alerts` 是**数组**（通知策略可分组聚合），逐条取 `fingerprint` 判重，**全部命中窗口才丢弃**（宁可多跑一条，不漏报）。去重结构用有界带 TTL 的实现。

### D9 每次报警独立会话

去重窗口之外的报警各起一个会话，历史不累积。**代价**：`sessions` 表按报警量增长；报警之间不共享上下文。

### D10 固定 `user_id` 用全零 UUID

报警没有 `from_userid`，无法像群聊那样派生。用 `00000000-0000-0000-0000-000000000000` —— 与列宽（`String(36)`）和全库 UUID 惯例一致。

### D11 最小跑法 + 输入构造

`kb_id=""`、`agent=""`（不检索、不绑定预设），复用站点管线。喂给 Agent 的 `query` 定模板：`alertname` + `level` + 每条 alert 的 `annotations.message`；模板进 `src/config/`。

### D12 报警轮禁用澄清（`ask_user`）

非交互轮次没有人类可答：`ask_user` 超时为 120s、单轮最多 2 次 ⇒ 会把分析拖到 4 分钟级，且以"超时文案"续跑、质量下降。报警轮**不注册 `ask_user`**。

**注意现状**：`CLARIFICATION_ENABLED` 目前是**死配置**（`src/config/settings.py:75` 定义后全仓无人消费），`ask_user` 在 `make_rag_tools` 里**无条件注册**。因此这不是翻开关，需要给 `start_turn` 开一个"按轮次覆盖工具集"的口子（`build_graph(tools=...)` 已支持覆盖，缺的是把参数透传上来）。

### D13 整轮超时

生成侧没有整轮时限，LLM 或出网挂死时事件流永不产生终态 ⇒ 报警永远不推也不兜底。编排层用 deadline 包住事件消费，超时即取消并走兜底。阈值进 `src/config/`。

### D14 失败、空回答、繁忙都判为失败 → 兜底

- 轮次抛错 / 超时 → 兜底
- 终态文本 `strip()` 为空 → 兜底（已知迭代触顶会产出空正文且落 `complete`，否则会往群里推**空气泡**）
- 并发 `TurnBusy` → 兜底（否则经全局异常处理器变 500，该次报警静默丢失）

### D15 主动推送分两段：受理占位 + 结论

主动推送**无入站 `req_id`**，因此**没有"流"**，也不能更新已发出的消息。分析可能持续数分钟，一段式会让群里长时间静默、无法判断告警是否进来。

因此在**入口去重之后**立刻推受理占位（`收到告警「{alertname}」，正在分析…`），分析完成后再推结论 —— **两条独立消息，不是同一气泡刷新**。

**约定**：占位消息**不写入**报警会话历史（纯转发）；占位发送失败**只记 warning，不阻断**分析；文案进 `src/config/` 的文案类。

**代价**：消息数翻倍 ⇒ 若主动推送存在频率上限，报警风暴下更易撞（见 OQ1 的 spike）。

### D16 兜底：模板化、带前缀、限长、不落历史

兜底**不整包 dump** 载荷：从已知字段渲染一段短文本（与 ARMS 模板形状一致），加前缀标记 `[原始告警]` 以便与结论区分，限制长度（上限进 `src/config/`），并**不写入**报警会话历史。

### D17 可见性靠"id 不匹配"，不做额外隐藏

会话列表按 `request.state.user_id` 过滤（该值由鉴权中间件对 `/api/sessions/*` 必然赋值）；报警会话用全零 UUID，**与任何登录用户的 uid 都不同** ⇒ 天然查不到。无需额外隐藏逻辑。

### D18 主动推送落在通道层，并明确其一次性语义

在 `src/channels/wecom/` 新增对外发送出口（封装 SDK `send_message`），由 `wecom-channel` 能力承载；上游只依赖"发到某个会话"这个语义。通道层需向调用方明确：**一次性发送、无流式、不可更新**，失败以结果返回。

### D19 渠道标识新增 `ALERT`

报警轮若沿用站点/企微的渠道值，排障时无法从日志渠道段与 Langfuse `metadata.channel` 区分。新增一个渠道值（`ALERT`）并在 `docs/agents/logging-rules.md` 的渠道表登记；入口设置 `current_channel`，否则会落默认值 `none`。

## Risks / Trade-offs

- **[`send_message` 未验证]** → 动手前先 spike：能否向**群**发出、目标有无限制（是否要求该群/该用户与机器人有过交互）、**频率上限**（两段式使消息数翻倍）。**这是本 change 最大不确定性**，结论回写 `wecom-sdk-facts.md`。
- **[群 `chatid` 从未实测]**（现有帧证据只有单聊）→ 首次部署时在目标群 @ 一次机器人，从 `sessions.title`（形如 `[企微·dev] 群聊 <chatid>`）读出明文填入配置。注意 `title` **仅首次落库生效**且超 256 字符截断。
- **[`alarmId` 稳定性未知]** → 见 D7；实测后校准，必要时改为"`alarmId` + 时间桶"或退化为每次生成。
- **[报警风暴]** → 入口去重 + 时间窗；不额外做排队。两段式使消息数翻倍，若主动推送有频率上限则更易撞。
- **[无鉴权入口的成本敞口]** 持有 token 者可构造不同 `fingerprint` 绕过去重、反复触发分析 ⇒ token 只放目标机 `.env`，泄露即轮换。
- **[`CLARIFICATION_ENABLED` 是死配置]** 本 change 若引入"按轮次覆盖工具集"，需注意不要与这条死配置混淆 —— 要么顺手把它接上，要么在文档里明确它当前不生效。

## Migration Plan

1. **先 spike** `send_message`（群发可用性 + 频率上限）；可与文档/实现并行，但结论决定通道层形态。
2. 代码实现 + 单测；配置项进 `src/config/`；渠道值登记进 `logging-rules.md`。
3. 目标机 `.env` 补告警 token 与目标群（**先同步 `.env`，再上新制品**）。
4. 阿里云侧：建「通用 Webhook」通知对象（URL 指向本接口、Header 带 token、可选自定义 body 模板）→ 在通知策略里引用 → 用「发送测试」验证连通。
5. 首次取群 `chatid`：在群里 @ 一次机器人 → 查 `sessions.title` → 填入配置 → 重新发布。
6. 冒烟：真实触发一次告警 → 群里**先收到受理占位、后收到结论**；再造一次分析失败 → 确认兜底转发带前缀。

**回滚**：停用 ARMS 通知策略即停止外发；代码侧无破坏性变更（新增端点与能力，不改现有链路）。
