## Why

用户投诉“付了钱没到账 / 被扣了两次 / 退款没回来”，这类问题**不是技术报错**：系统可能一切正常，但业务状态与用户预期不一致。它和 `trace-diagnosis` 的三类问题（5xx / 4xx / 模型答错）在三个方面根本不同：

1. **数据域不在本系统**——订单、支付流水、回调、退款都在支付系统（Java），本仓只有用户会话与机器人回答。
2. **判定规则是业务规则**——“重复扣款”不是异常，“已支付但订单状态未流转”也不是 bug，而是状态机与对账口径问题；`root_cause` 那套技术枚举表达不了。
3. **合规要求更高**——涉及金额、银行流水、可能的证件信息，脱敏与访问控制比技术日志严一档。

现在值班同学遇到这类投诉只能人工翻系统，结论不落档、不可复用。

## What Changes

- 新增**投诉受理入口**：输入为订单号（或用户 + 时间窗 + 投诉描述），输出一份“事实 + 处置建议”报告。
- 新增**跨系统取证**：订单状态机流转、支付流水、支付回调记录、退款单、以及对应用户的会话记录（是否被机器人误导）。
- 新增**业务规则判定**：按规则表判定情形——重复扣款 / 已扣款未到账 / 支付超时 / 退款失败 / 订单状态卡滞 / 与机器人答错相关。
- **复用 `trace-diagnosis` 的报告骨架**（证据引用、无法判定即出口、只读），但不复用其根因枚举。
- 产出**处置建议**（补单 / 发起退款 / 联系渠道 / 人工核对），只出文本，不执行资金操作。

## Capabilities

### New Capabilities

- `payment-complaint-triage`：投诉取证（跨系统只读）、业务规则判定、处置建议、报告与落库。

## Impact

**代码**

- 新增 `src/complaint/`（取证、规则、报告）；复用 `src/rca/` 的 Evidence / Report / validator
- 新增只读适配层：支付系统接口（形态待定，见下）

**接口**

- 新增对内工具：`complaint_lookup`（按订单号/时间窗）
- 对外沿用企微通道

**依赖**

- **支付团队提供只读接口**：按订单号查订单状态、支付流水、回调与退款记录。形态二选一（HTTP 只读接口 / 独立 MCP 实例），未定
- 与 `trace-diagnosis` 单向依赖：判断“是否机器人误导”时调用其诊断能力

**风险**

- 金额与个人信息泄露：报告默认只出摘要，明细需二次展开并留痕
- 跨系统数据不一致（支付侧与本地会话时间不同步）：报告必须标注时间来源
- 规则误判导致错误处置建议：规则表需人工确认后才给出“建议退款”

## 非目标

- 不执行退款、补单等任何资金操作
- 不做对账系统、不做结算
- 不做跨支付渠道的统一抽象
- 不覆盖非支付类业务投诉（如服务态度、功能咨询）

## 待定（阻塞实施）

1. **支付侧接口形态**：只读 HTTP 还是独立 MCP 实例；字段清单与鉴权方式
2. **投诉入口**：企微群内由值班发起，还是业务侧表单提交
3. **证据保留**：投诉报告含金额与用户信息，保留期与脱敏规则需单独裁定（与出域审计同一口径）

## 验收判据

1. 给一个真实订单号，能产出「资金在哪 + 是否重复 + 下一步动作」三段结论
2. 任一条断言可回溯到证据（订单/流水/回调的具体字段）
3. 证据不足时输出"无法判定"并说明缺哪份数据
4. 全程不触碰资金操作接口（代码层面无写方法）
