# design — timeout-and-degradation-hardening

## Context

三类模型（LLM / Embedding / Rerank）**直连 Provider**（ADR-0020），差异收敛在 `src/infra/llm/provider/`（ADR-0021）。该层是"唯一构造产地"：`build_chat` / `build_embeddings` / `build_rerank`，`src/models.py` 是薄委托门面。角色共 6 个：`main` / `classify` / `summary` / `judge` / `embedding` / `rerank`（`resolve_role` 解析，`registry.yaml` 存 provider 固有事实）。

**先例**：ADR-0024 在**裁判一条链**上验证过完整口径（细粒度超时 + SDK `max_retries=0` + 本层有界重试 + 失败留原始响应），实测 21 题全量 `1h41m → 29m48s`、失败行 `5/21 → 3/21`。本次是**把口径推广 + 补降级**，不是新发明。

**现状（已逐一核过代码）**：

| 模型/角色 | 超时 | 重试 | 降级 | 留痕 |
|---|---|---|---|---|
| `main`（流式） | ❌ | 仅 SDK 2 | ❌ | ❌ |
| `classify` | ❌ | 仅 SDK 2 | ❌ | ❌ |
| `summary` | ❌ | 仅 SDK 2 | ❌ | ❌ |
| `judge`（LangChain 路径 `get_judge_llm`） | ✅ 平铺 300 | — | — | — |
| `judge`（现代栈 `build_ragas_judge`） | ✅ 细粒度 | ✅ 本层 3 + SDK 0 | — | ✅ |
| `embedding`（查询/入库） | ❌ | 仅 SDK 2 | ❌ | ❌ |
| `rerank` | ❌（SDK 无该字段） | `with_retry(3)` | ✅ 退化距离排序 | ✅ 三事件 |

**两个既有事实容易被误读，先行澄清**：

1. 池 A-05 写「✅ 模型调用：`@with_retry` 指数退避重试」—— **不成立**：`with_retry` 全仓**只有一个调用点**（`src/rag/retrieval.py:171` 的 rerank）。
2. 池 A-03 写「Embedding 不可用 → 退 **BM25**（需先建倒排索引）」—— **过时**：词法路已是 PG 全文检索（`ChunkRepo.search_lexical`），退化**不需要新建任何东西**，只需"跳过 dense 单走词法"。

## Goals / Non-Goals

**Goals:**

1. 让每个外部调用的失败**在可判定的有限时间内**发生（A-05），且代价可见（事件 + 时长）。
2. 让每类依赖在失败时**有明确动作**，并让用户**知道**（A-03）。
3. 把口径收敛到**尽可能少的归属地**：超时值一处、异常分类一处、事件一处、文案一处。

**Non-Goals:**

- **不做熔断（A-02）**：熔断是"连续失败后快速失败"的状态机，与超时是两件事。没有它，代价只是"依赖挂掉时每次调用各付一次超时"（见 D8）；这是**有意接受的代价**。
- **不做限流（A-01）**、不做 Chaos Engineering（池 A-03 最后一条）。
- **不做进程内模型 fallback**（D9）：LLM 失败的处置是"重试 → 返回检索原文 + 告知"，不切备用模型。
- **不改 fork 的三层超时**（已实现且好），只**对齐词表与命名**。
- **不引入模型网关**（ADR-0020 不变）。

## Decisions

### D1：不抽"一个新的层"，而是三处分工 —— 超时进 provider 层、判定抽无状态原语、动作留调用点

```
① 构造/配置面   provider 层（已存在）      build_* 显式传 timeout/retry；值按角色取自 settings
② 判定/重试原语 ★唯一新增模块（无状态）    retry_policy：异常分类 + 有界 + jitter（sync/async 两版）
③ 降级动作+出口 各调用点（每依赖语义不同）  出口收敛：事件 → log_event_specs；文案 → const.py
④（未来 A-02）  熔断状态机 ← 只有它值得抽成「有状态的层」
```

**理由**：

- **超时是构造参数**，唯一产地已经是 `build_*`（ADR-0024 的 `build_native_client` 即此模式）⇒ 补参数即可，无需新层。
- **降级抽不出来**：动作是每依赖独有的，且要触摸业务状态（跳过 dense / 返回检索原文 / 改 SSE 事件 / 写 `status`）。硬抽只能退化成 `degrade(call, on_failure=回调)` —— 把回调搬了个家、多一个概念，**假内聚**。真正可收敛的只有它的**两个出口**。
- **"降级不进 provider 层"有 ADR 依据**：ADR-0020/0021 明写 provider 兼容层「**不是网关**（不做路由 / fallback / 限流）」。超时参数进去不违反（那是"构造客户端的参数"）；降级动作进去等于把手伸进业务语义，正是当初拒掉的。
- **本仓惯例是小入口模块**：`infra/llm/tracing.py`（Langfuse 唯一入口）、`infra/llm/token_count.py`（唯一计数入口）、`provider/thinking.py`（唯一思考参数产地）。②照这个规格做。

**落点（已定 2026-10-16）**：② 迁到 `src/infra/retry_policy.py`，并**一次性改掉唯一调用点**（`src/rag/retrieval.py:171`，全仓仅此 1 处）⇒ **不保留 `src/models.py` 的别名转发**（留别名会制造两个入口，与「唯一产地」惯例相悖；且它现住在模型门面里本身就是归属错误）。

### D2：超时/重试值**按角色**放 `settings`，**不进 `registry.yaml`**

**理由**：

- `registry.yaml` 装的是 provider/模型的**固有事实**（`context_window` / `pricing` / `tokens_per_cjk_char` / embedding batch / 端点 / 密钥名）—— 换 provider 会变。
- 超时是**我们的 SLO 取舍**：同一 provider 的 `main` 与 `classify` 取值不同 ⇒ 它是**角色属性，不是 provider 属性**；进 registry 会把"可调策略"冻进数据面（改一次要重建镜像）。
- 现任裁判超时就是 env（`RAGAS_HTTP_TIMEOUT_*`）—— **但那是评测链的键**，归属见下。

**粒度 = 角色**（D9 的开放问题见下）。一刀切是明确错的：`classify` / `summary` 是短结构化调用（ADR-0024 实测裁判 p95 = 55.3s），给 600s 等于"卡 10 分钟才失败"。

**键名归属（第三轮 I6 —— 修掉一处真源矛盾）**：本变更 **SHALL NOT 复用评测链的 `RAGAS_*` 键名**，生产侧角色的超时/重试 SHALL 用**自有键名**（仍住 `settings`）。理由：D17 声明"两侧不得互相覆盖对方的取值族"，而评测链（`deepeval-bridge-eval`）已定把这族键"**复用 · 承载点换位**"到 `ChatOpenAI(http_client=…)` ⇒ 若生产也挂在同一批键上，**对方改键即静默改生产**，真源声明自相矛盾。⇒ "沿用 ADR-0024"的准确含义是**沿用其取值与形状**（细粒度 `connect/read/write/pool` + 关 SDK 重试），**不含键名**。

### D3：主循环补的是「生成任务级 idle」，**不是**回退 SSE 订阅层的 180s 空闲收流

三层必须分清，否则实施者会以为是回退：

| 层 | 谁的空闲/失控 | 现状 | 本次动作 |
|---|---|---|---|
| SSE 订阅 `_subscribe_events` | **客户端**收不到事件 | `max_idle=None`（主流）/ 180s（resume 僵尸兜底） | **不动**（有意解耦：生成还在跑就不该断，`sse-stream-resilience` 已固化） |
| 生成任务 `fork_stream` | **子代理**不吐事件 / 跑太久 / 轮次多 | ✅ idle 60s / total 240或600 / turn | **不动**，只对齐命名 |
| 生成任务**主循环** | **主 agent** 不吐事件 | ❌ 无 | ← **补这一格** |

**形状照抄 `fork_stream`**（判据 = 事件条数不增长）。注意差异：fork 是"到点 → **中止** + 记 reason"，而本变更**档 1 只记不中止**（见下）。

**词表约束（2026-10-16 修订 —— 上一轮改 D12 时漏改了这里，评审 B1 抓到）**：`DelegateStopReason` 的注释确实写着「契约/文档/前端文案**不得另起原因词**」（spec `delegate-execution-controls`），**但该枚举的语义是「fork 结束原因」**。本变更档 1 **不产生"停止"** ⇒ **不套用该枚举**，改用自有降级事件 `reason = generation_idle`（见 D6 取值集合）。那条"不得另起原因词"的约束**在档 2 引入真正中止时才需要正面处理**（届时评估复用或扩展枚举并同步该 spec）。

**动作分两档**（降低风险）：
- 档 1（**已落地，P3**）：**事件 + 用户可见文案**，不动控制流 —— 起点是 `_silence_watchdog`（D-11 挂号待清的临时埋点，**只打印任务栈**），P3 已把它**转正**为 `src/services/agent_service.py` 的 `_idle_guard`（判据 = 缓冲**事件条数**不增长达阈值 ⇒ 记 `degraded(reason=generation_idle)` + 推 `status`，**不中止**）。
- 档 2（后做）：**取消/降级**，需接 `task_registry` 的取消路径。

### D4：流式超时 = **传输层单一预算 + 业务层事件守护**（两层，不得互相声称对方的能力）

> **修订（2026-10-16，架构评审 F1 的 Blocker）**：初版写"`read` = 流间隔；首 token 用独立守卫"，并给出 `read=60s` + 首 token=180s。**该组合不可满足** —— HTTP `read` **覆盖首个字节之前的等待**（排队 / prefill 均计入），所以 60s 必然先触发，180s 的首 token 守卫**永远不会生效**。

| 层 | 表达方式 | 约束 |
|---|---|---|
| **传输层**（httpx `read`） | **单一预算**：「请求发出 → 字节到达」，**同时覆盖首字节之前的等待** | 须 **< nginx `proxy_read_timeout` 300s**；SHALL NOT 解释为"仅流间隔" |
| **业务层**（事件守护） | 判据 = **事件条数不增长**；两档阈值（首个事件前 / 之后） | 这是**面向用户**的判据，也是"首 token 守卫"的实际承载 |
| **整请求** | **不设** | 长回答天然数分钟，设了就是误杀 |

⇒ 分层含义：传输层是**兜底**（防连接级挂死），业务层才是用户可感"卡住"的判据（两档阈值见 D15）。

**重试 × 流式的硬约束**：流一旦开始输出，**不得重试**（会重复输出给用户）。⇒ 重试窗口**只在首个 chunk 之前**。这条把 A-05（重试）与 A-03（降级动作）在设计上焊在一起；配套的"**不得只关不加**"见 D16。

### D5：异常分类收敛为无状态原语；补 jitter 与 async 版

**现状缺陷**：`with_retry` 的 `retryable_exceptions` 默认 `(Exception,)` ⇒ 400/401/403、`ValueError` 全被重试；而它**全仓只有 1 个调用点**（`src/rag/retrieval.py:171` 的 rerank），所以受害面目前**限于精排**。

> **证据勘误（2026-10-16，架构评审 F7）**：初版把"检索上下文为空被白跑 `3 × 3 = 9` 次"记作 `with_retry` 的代价 —— **错挂**。该数字出自**评测链**的 `_score_metric_with_retry`（`src/cli/eval_ragas.py:423`，用 `RAGAS_METRIC_MAX_ATTEMPTS`，**独立于** `with_retry`），且那个函数归 `deepeval-bridge-eval` 处置。⇒ 本条**方向仍成立**（默认全量捕获会把 4xx / `ValueError` 一并重试），但**改 `with_retry` 的默认值修不了评测链那起事故**；评测链属**同类问题的另一个实例**，不在本变更范围。

**判据（按"重试是否会改变结果"）**：

| 类 | 处理 | 例 |
|---|---|---|
| **不可重试** | 立即失败 | 输入校验类（`ValueError` 等，且**失败耗时 ≈ 0s**）、鉴权/权限（401/403）、请求格式（400/422） |
| **可重试** | 有界 + 退避 + jitter | 超时、连接错误、429、5xx |

**适用范围（必须写明，否则与在途 change 的口径看起来互相矛盾 —— 拉 dev-wsl 时发现）**：本表只约束**生产链路**（`main` / `classify` / `summary` / `embedding` / `rerank`）。**评测链的 429 / 403 口径归 `deepeval-bridge-eval`，与生产相反且各自成立**（依据 D17 的真源声明）：

- **429**：评测链**不重试** —— ragas 框架层已对 `openai.RateLimitError`（= HTTP 429）重试 ≤10 次（`ragas/llms/base.py:325-335` 设 `exception_types`、`ragas/run_config.py:52` `max_retries=10`），外层再叠是 **10×3 放大**；而**生产链路没有框架层重试** ⇒ 必须由本层重试。
- **403 额度类**：评测链**由外层重试**（ragas 不重试它，外层是**唯一**一层）；生产链路**不重试**（重试必然再失败 ⇒ 转降级 + 告知）。

⇒ 两处**是分工、不是矛盾**。**本表与 `timeout-policy` 规格的措辞均不得被读作覆盖评测链**。

**判据与取证归评测链（2026-10-16 用户裁定）**：`401/403` 在本侧**一律不重试**（规则不变）；但 403 既可能是鉴权失败、也可能是**额度耗尽**（历史冒烟实测即 403 + `AllocationQuota.FreeTierOnly`），**要分开就必须有响应体判据** —— 该**判别与取证整体交给 `deepeval-bridge-eval`**（它已有可读状态码 / 响应体的 hooks 证据机制）。⇒ 本变更**按单一文案落地**（`provider_unavailable`）：**不再要求在本变更内先做取证实测**，**也不保留两行**。

**另补（第三轮 I2）**：**429 / 5xx 重试穷尽**也是降级的一种 —— 它需要自己的 reason 与文案（取值表已补 `upstream_exhausted`），此前漏了。

**另补两项**：
- **jitter**：现为固定 `initial × backoff^(n-1)`（`1s → 2s → 4s`），多请求同时失败会**惊群**。加随机抖动。
- **async 版**：现 `with_retry` 用 `time.sleep`，**只可用于同步函数**（rerank 恰好包在 `asyncio.to_thread` 里才没炸）。给异步调用点（未来 LLM 重试）必须有 await 版，否则阻塞事件循环。

### D6：降级矩阵 —— 动作留调用点，两个出口收敛；**不复用 `CAPABILITY_DEGRADED`**

| 依赖 | 失败判定 | 动作 | 可行性 |
|---|---|---|---|
| Rerank | 超时 / 异常 | **已实现**：退化向量距离排序（`rerank_results` + 工具层 `wait_for(RERANK_TIMEOUT=5)`） | ✅ 已做，只需对齐事件 |
| Embedding（查询） | 异常 / 超时 | 跳过 dense，**单走词法路**（PG FTS 现成） | 低（需改 `gather` 语义，见 D7） |
| 向量库 | 异常 | "知识库暂不可用" + 告知用户 | 低 |
| LLM | 首个 chunk 前失败 | 重试（仅可重试类，D5；**窗口仅限首个 chunk 之前**，见 D4）→ 仍失败则：**本轮已取得检索结果** ⇒ 返回检索原文 + 明确告知；**无检索结果**（如首次模型调用即失败）⇒ **仅明确告知** —— 此时并不存在"检索原文"，不得承诺返回它；**不切备用模型**（D9） | 中 |
| Prompt 来源 | — | 现状无远端（Git YAML 唯一源）⇒ **不适用** | — |
| 全部 | 任何降级发生 | **留痕 + 用户可见文案** | 低（口径见下） |

**两个出口**：
- **事件** → `src/core/log_event_specs.py` 的 `EVENT_SPECS`（**唯一归属**，ADR-0024 决策 6 已确立此口径）。
- **用户文案** → `src/config/const.py`（`SSEInteractionTexts` 等已在用，`src/rag/retrieval.py` 即引用）。
- **取值集合**：`reason` 取值与用户文案**不得由实现自造** —— 清单已落进规格 `specs/degradation-policy/spec.md` 的「降级原因与用户文案的取值集合」表（架构评审 Q3：不允许实现层发明用户可见行为）。

**原因与文案解耦**：`reason` 表达**原因**（日志判据用），文案表达**交付产物**；只要本轮**已取得检索结果**，无论 `reason` 是可用性类还是 `llm_unavailable_no_context`，用户文案一律取 `llm_unavailable_with_context` 并附检索原文（唯一例外：流已开始输出 ⇒ 不重放原文）。

**⚠️ 不得复用 `CAPABILITY_DEGRADED`**：它的现有语义是"`/skills`、`/agents` 清单读失败"（`src/api/capabilities.py`，字段 `resource`/`reason`）。复用到"依赖降级"会污染能力面板的语义。要么新开事件（如 `dependency degraded`），要么在 spec 里显式扩展语义并区分 resource 取值域。

**先产出的中间物**：一张「降级清单」（依赖 → reason 枚举 → 是否用户可见 → 文案键）。没有它，D6 的动作与 D3 的 idle 文案都无处挂。

### D7：`gather` 语义要改，否则"退化为词法单路"根本不成立

现状 `src/rag/retrieval.py:86`：`await asyncio.gather(dense_coro, lexical_coro)` —— **未传 `return_exceptions`** ⇒ dense（查询 embedding）一抛，整个 `search` 就抛，**词法结果被连带丢弃**。所以"Embedding 失败 → 只走词法"必须先改这里的失败语义（任一路失败仍返回另一路，并记事件标明某路降级）。

这同时让 `HYBRID_DONE` 事件里已有的 `dense_count` / `sparse_count` 成为**降级可观测**的现成载体（「某一路长期为 0」是可发现的）。

### D8：没有熔断的代价（明确接受）

无 A-02 时：依赖挂掉后**每次调用都各付一次完整超时**（而不是快速失败）。A-05 把超时变成"可判定的有限时间"后，A-03 的动作本身成立；熔断只是省掉"重复付超时"的成本。**故 A-03 + A-05 可独立于 A-02 落地**（池中 A-03 标注的依赖 A-02 不是硬前置）。

## Risks / Trade-offs

- **行为一次性变化**（因为不做"隐形变显式"的中间步）：必须靠**改前/改后对照实测**兜（ADR-0024 的 E9 表就是模板：配置 → 墙钟 → 失败行），而不是靠分两次提交。
  - 附注：池 A-05 原文建议"先取与现状等值的默认值（零行为变化）再改值"。本设计**有意不拆**：等值 = 显式写出 600s + 2 次重试，**本身零收益**（且 ADR-0024 已证该组合有害）；而拆分原本要分开的"形状风险"在裁判路径已被验证。**代价必须知道**：数值风险只能靠实测对照兜。
- **会改到评测的选手侧**：评测的"选手"就是 `get_llm()` 即生产模型 ⇒ 给 `main` 加超时会同时作用于评测。需定"评测是否跟随生产取值"（开放问题）。
- **`main` 流式不能重试已输出的部分** ⇒ 若首 token 之后断流，用户可能拿到半截回答。属**已知取舍**（另一条路是"静默重生成"= 重复计费 + 可能不一致）。
- **idle 保险丝取值难**：太紧会误杀深度思考（主链路开思考时首个 token 可能很久）。ADR-0024 的实测里有"开思考 + 8192 → 21 题 5/21 超时、1h31m"的记录可作参照，但**那是裁判场景**，主链路需单独标定。
- **`rerank` 的超时是"半成品"**：工具层 `wait_for(5s)` 只**放弃等待**，底层同步 HTTP 仍在 `to_thread` 里跑（`asyncio.wait_for` 不取消线程）⇒ 用户侧延迟有界，但**重复挂死会让线程堆积**。本次是否一并处理，见开放问题。

### D9（2026-10-16 修订）：**不引入进程内模型 fallback** —— 但必须**区分「抖动」与「长时不可用」两个尺度**

> **修订说明**：初版 D9 只论证了"短时抖动"，把"长时不可用（小时~天）"一并归入"不做"，**论证不完整**。本节按尺度拆开，并记录由此暴露的一个**今天就在发生**的必修缺陷。

#### 尺度一：抖动（秒 ~ 分钟）→ **重试，不 fallback**

**理由**：① 流式下 fallback 只在**首 token 之前**可用（D4：首 token 后不可换模型），而首 token 前失败多为连接/限流类，**重试即可解**；② 换模型会致契约变化（`temperature`/`top_p` 被 400、思考档位失效），抖动场景下用"换模型"解"另一个模型更快"是错配。

#### 尺度二：长时不可用（小时 ~ 天）→ **必须有明确方案**（初版未论证）

两个面能力完全不同：

| 面 | 是否有备选绑定（`registry.yaml` 实测） | 长时不可用的处置 |
|---|---|---|
| `embedding` / `rerank` | **无** | **只能语义降级**：退词法路 / 跳过精排（A-03 动作天然覆盖，见 D6/D7） |
| `main` / `classify` / `summary` / `judge` | **有**（`deepseek` 已绑定这四个角色；`dashscope` 绑定全部 6 个） | **选 (A)**，见下 |

**决策（2026-10-16，用户拍板）：(A) 快速失败 + 明确告知 + 告警 + 人工部署级切换 —— 不做自愈。**

- **产物不是"什么都没有"**：LLM 不可用时给 **"检索原文 + 明确告知"**（即 A-03 已定的动作）⇒ **对长时不可用同样有效**，保住溯源、零编造，只是拿不到自然语言答案。
- **依据**：用户确认 ①「降级产物可以就是检索原文 + 告知」、②「分钟级可人工介入切换」（部署级切换 = 改 `.env` 的 `LLM_PROVIDER` + `--force-recreate`，约 2 分钟）⇒ **自愈的收益（省掉分钟级窗口）小于它的代价**。
- **被否的替代方案（记录以免日后重开）**：
  - **(B) 进程内自动换 provider**：机制成本低（两 provider 已配好），但 ① **不能落在 provider 层**（ADR-0021 明写该层不做 fallback）⇒ 必须落在其**之上**；② 与 ADR-0020「放弃跨 Provider fallback」有**精神张力**；③ **质量差异无法自动判定** ⇒ 金融域"静默降质"比"暂不可用"更糟。
  - **(C) (B) 的收敛版**（只在"可用性类错误 + 首 token 之前"触发，并**透出**在用备选模型）：是 (B) 的**可接受形态**；本次不启用，**若将来 SLO 要求缩短不可用窗口，优先按 (C) 形态**实现。
- **归属（已定 2026-10-16）**：**"抖动不 fallback"** 是 ADR-0020 的直接应用（不新开 ADR）；**"长时不可用也不 fallback"** 是带代价的负向决策 ⇒ **要落一条新 ADR，但编号必须让开**：在途 change `deepeval-bridge-eval` 的 design 明写"**追加新 ADR 取代 ADR-0024**" ⇒ `0025` 大概率被它占用，而 `check_adr` 要求编号**连续**、重编号必须与合并**同一提交** ⇒ **抢号会制造返工**（要同步文件名 / 标题 / README 索引 / 引用四处）。故：**先由本文承载，排在 `deepeval-bridge-eval` 落地之后取下一个可用编号**（若它最终不落，则用 `0025`）。

#### ⚠️ 必修项：上游可用性类错误**今天的实际行为**（2026-10-16 按代码复核，**修正本处初版的不实表述**）

### D10：超时粒度 = **角色级** + 查询 embedding 在**调用点覆盖一次**

**理由**（同 D2）：角色是现成的解析维度（`resolve_role`），6 个角色与场景基本一一对应；唯一"同角色两语义"的是 `embedding` —— 查询（在线、单条、**失败可退词法**）与入库（离线、批量、可重试或标 `failed`）**失败语义不同**，故合理取值必然不同，这正是要给查询路**紧**超时的原因。

**反对**引入"场景"维度：配置矩阵从 6 变 N×M，而收益只落在 1 个角色上。

**覆盖落点**：`QueryEmbedder`（可注入入口，`src/infra/db/vector_store/pg_store.py`）—— 因为查询侧每次 `get_embeddings()` 新建实例（E6），超时是按实例设的。

**范围排除（已定 2026-10-16）**：`embedding` 客户端**复用**（每次重建连接池，E6）**不纳入本变更** —— 它是**性能**问题而非可靠性问题，混进来会让 D11 依赖的「改前/改后对照」**失去单变量**。**须登记为 follow-up（不丢）**。

### D12：idle 保险丝 = **转正 `_silence_watchdog` 到生成任务侧，阈值按思考档位分档**

**理由**：

- 它已在**对的层**（生成任务的事件缓冲）、用**对的判据**（缓冲**事件条数**不增长 —— 比"字节间隔"更贴近用户感知，例如模型只在吐 tool_call 而不吐 token）。
- 它是 D-11 挂号的**待清临时埋点** ⇒ 要么删、要么转正；转正是把它从成本变资产。
- **不落 SSE 层**：那层是"客户端订阅"语义，这里管的是"生成任务是否失控" —— 混了正是 D3 要防的误读。
- **阈值必须分档**：主链路开思考时首 token 可能很久（ADR-0024 实测开思考导致大面积超时）⇒ 像 `DELEGATE_TOTAL_TIMEOUT_S=240` / `..._THINKING_S=600` 那样按档位分（**现成先例，照抄**）。

**分两档落地（已定 2026-10-16：本变更只做档 1）**：**档 1 = 事件 + 用户文案**（不动控制流，风险极低）；**档 2 = 取消 / 降级** 需接 `task_registry` 的取消路径，会与 `request-abort` 的既有契约「**仅 cancel 中止生成**」交叉 ⇒ **档 2 登记为 follow-up**。理由：用户当下的痛点是"**没人告诉我**"而非"没人打断它"，档 1 已能兑现。

**原因词的处理（修订，架构评审 F4）**：**档 1 不产生"停止"，故 SHALL NOT 声称"复用 `DelegateStopReason`"** —— 该枚举的 docstring 限定其语义为「**fork 结束原因**」，套到"只是记录一次静默"上名不正（也与 D6「不复用 `CAPABILITY_DEGRADED` 以免污染语义」的原则自相矛盾）。改法：档 1 发**自有降级事件**，`reason = generation_idle`（已在 D6 取值集合中登记）；**档 2** 引入"真正停止"时，再评估是否复用或扩展该枚举。

### D13：rerank 超时**下沉到客户端**，拆独立任务、独立验证

**决策**：本次一并修。

**理由**：

- 这本是 A-05 的题中之义（"每层都有超时"）；现状只有外层 `wait_for`、底层无超时 ⇒ 严格说**不算已完成**。
- **代价真实且隐蔽**：`asyncio.wait_for` **不取消** `to_thread` 里的线程 ⇒ 每次挂死占一个线程；而 rerank 是**每轮检索都调**的高频路径，上游抖动时会占满 `to_thread` 的默认线程池 —— "看起来降级成功、实则资源泄漏"，比不降级更难发现。

**实现路径（2026-10-16 实测修正，成本比原估低）**：`DashScopeRerank` 的 pydantic 字段只有 `['client','model','top_n','dashscope_api_key']`、`model_config['extra']='forbid'` ⇒ **构造器传 `timeout` 会直接报错**（"无该字段"确证）。但：① 它调用的唯一出口是 `self.client.call(...)`；② dashscope SDK **原生支持 `request_timeout`**（`dashscope/api_entities/api_request_factory.py:33` 会 pop 出来传给 HTTP 层）。

⇒ **走「自定义 `client` 适配器 + 注入 `request_timeout`」**：极小改动、保留 LangChain 的解析逻辑、不新增 HTTP 客户端。⇒ **原"改动面大、需换底层直调"的估计作废**；仍保留「独立任务 + 独立验证」。

> **数值必须嵌套（修订，架构评审 F5）**：初版写"**它根治而非绕过**" —— **overclaim**。rerank 实为**三层超时叠加**：内层 `request_timeout=5s` × `with_retry(attempts=3，退避 1s/2s)` ≈ 最坏 **18s**，而外层 `wait_for(RERANK_TIMEOUT=5s)` 会在 **5s** 先放弃 ⇒ 线程照跑到约 18s，"线程自己退出"**不成立**（只是从"无限"变成"有界"，仍会堆积）。
> ⇒ **修正**：rerank **attempts=1**（重试对"一次 5s 超时的同步调用"收益很小，且它是高频路径），让**内层 5s 成为唯一预算**；外层 `wait_for` 提到 **6s**、仅作双保险（**必须 ≥ 内层预算**，否则又会先放弃）。

### D14：评测**跟随"形状"、不跟随"数值"**

**决策**：评测侧复用同一套配置骨架（角色级 + 显式化 + 关 SDK 重试），但**各场景各自取值**（评测离线批量可宽，生产在线须紧）。

**理由**：

- 口径要分清：ADR-0022/0023 的"**评估检索镜像生产**"说的是**输入范围**（检索哪些文档），不是时延预算；而 ADR-0024 明确警告"不要照搬评测数值"。
- **跟随数值的危害**：评测的"选手"就是 `get_llm()` ⇒ 用生产的紧超时会把**生产环境的超时**当成**模型能力**来打分（timeout → 指标失败/NaN），污染质量结论（ADR-0024 原话："超时不当会把分数变成失败"）。
- **完全不跟随的危害**：测的是一条比生产宽松的链路，"镜像"失去意义。
- 分层判据：**形状 = 能力**（谁有超时、重试怎么分类、SDK 重试关掉）⇒ 跟随；**数值 = SLO 取舍** ⇒ 不跟随。

**落地（第三轮开放问题 2：此前只有原则、没有落点）**：① 取证时**记录本轮时延预算配置**，报告才能判断"这是超时导致还是模型能力"；② 评测的"选手"就是 `get_llm()`（生产模型构造）⇒ 评测侧 SHALL **显式覆写角色超时**（不继承生产在线取值）并把该覆写**写入报告** —— 否则"不跟随数值"只是句口号。

### D15：首 token 守卫与 idle 保险丝 = **同一机制、两档阈值**

**决策**：不建两个机制。判据同源（**事件条数不增长**），只是所处阶段不同：

| 阶段 | 阈值（首版） | 等价于 |
|---|---|---|
| 首个事件**之前** | **非思考 60s / 思考 150s** | 「首 token 守卫」的实际承载（D4：传输层 `read`=180s 只是兜底）。**两档都必须 < 传输层 read**，否则该档永不负责（评审 B2）；**且必须按思考档分档**（D12），否则精度落空、正常思考轮误触发（第三轮 I1） |
| 首个事件**之后** | **非思考 30s / 思考 60s** | 「流间隔守卫」的实际承载（同样按思考档分档） |

**理由**：`_silence_watchdog` 本来就同时覆盖"**一次事件都没有**"与"**中间断了**"两种情形 ⇒ 两套机制会重复实现同一件事，还可能出现"两个守卫互相打架"。⇒ **一个机制 + 两个阈值常量**，各自再按思考档位分档（D12）。

**两档的实际分工（P3 实测补充，2026-10-16）**：`first` 档的真实语义是"**启动阶段就完全卡住**"（首个事件之前一直无事件）。正常轮次里首个 `status`（"正在思考…"）事件通常在百毫秒级到达 ⇒ **该档几乎不会在正常轮次触发**，日常长静默由 `gap` 档负责。实测：阈值压到 0.2 秒仍不触发、0.02 秒才触发（P3 冒烟 C2）。**这与 spec 的表述一致**（"阈值内未产生任何事件"），不是该档失效 —— 但选错预期会误判"守卫没生效"。

**文案语义必须匹配"不中止"（评审 B2 补充）**：档 1 **不中止**生成，故其用户文案 SHALL NOT 写成"已超时"这类**终态**措辞（否则用户收到"超时"却仍在等待，比不说话更糟）；应为"仍在处理中 / 长时间无输出"类**过程**提示。终态措辞只在**档 2**（真正中止）可用。

### D16：主链路 LLM 的**本层**重试（挂点 + 「首个 chunk」守卫）

**背景（架构评审 F2）**：本变更把 SDK 重试关到 0；若不补本层重试，主链路 LLM 会从"SDK 重试 2 次"变成**零重试** —— 与"抖动 → 重试"的目标相悖，且是**相对现状的倒退**。

**决策**：为 `main`（及同类对话型角色）在**本层**实施**异步、有界、仅在首个 chunk 之前**的重试。

- **挂点（2026-10-16 收窄到具体 seam，评审 I1）**：必须是**模型对象级包装** —— 包住 `build_chat` 产出的模型对象，**转发 `bind_tools`**，并在 **`_astream` 内**做"已产出即不重试"守卫。**两条更省的路都不通**：① `Runnable.with_retry` **明确不重试 stream**（`langchain_core/runnables/retry.py:378` 原文注释："stream() and transform() are not retried because retrying a stream is not very intuitive."）；② 循环 middleware 的 `awrap_model_call` 只拿得到 `ModelResponse`、**拿不到 chunk**，实现不了该守卫。**SHALL NOT** 落进 provider 兼容层内部（ADR-0021：该层不做 fallback / 重试策略）。
- **守卫（硬约束，非优化）**：包装层 SHALL 记录"是否已向调用方产出过 chunk"；**一旦产出过即不重试**，否则会重复输出给用户。
- **可观测**：每次重试 SHALL 留痕（attempt 序号）—— 理由同 ADR-0024 决策 3：本层重试的价值之一正是"**可见**"。
- **为何不走"保留 SDK 重试"这条更省的路**：ADR-0024 已证 SDK 重试是**静默的乘法放大**（一次逻辑调用实际发 3 次 HTTP，日志只看得到墙钟变长）。本变更的目标就是让失败**可判定、可观测**，故应把隐匿放大换成我们层的可见重试，而不是把问题留在 SDK 里。

### D17：与在途 change 的定序，与「超时策略」真源声明

**问题（架构评审综合发现）**：在途的 `deepeval-bridge-eval` 与本变更**动同一批文件**、且**都在主张"超时策略"** —— 它计划**删** `build_native_client`、把 `RAGAS_HTTP_TIMEOUT_*` 改嫁到 `ChatOpenAI(http_client=…, max_retries=0)`、并**追加新 ADR 取代 ADR-0024**；本变更则动 `build_chat` / `build_embeddings` / `build_rerank`。

**真源声明（本变更立场）**：

- **生产链路**（`main` / `classify` / `summary` / `embedding` / `rerank`）的超时与重试，真源是**本变更**；
- **评测链**（`RAGAS_*` 族、judge）的真源是**它**；它把 `RAGAS_HTTP_TIMEOUT_*` 改嫁到 `ChatOpenAI` 属**评测链内部的承载点换位**，不改生产语义；
- 两侧**不得**互相覆盖对方的取值族。
- **已实测撞到一例（2026-10-16 拉 dev-wsl 时）**：评测链定「**429 不重试**、**403 额度类由外层重试**」，与生产口径**相反但各自成立**（评测链有 ragas 框架层重试 ≤10 次，生产没有）⇒ 已在 D5 与 `timeout-policy` 规格写明**适用范围**，避免被读成矛盾。**这属于跨 change 口径边界，本变更的机检（`docs/tmp/check-change-consistency.py`）读不到**（它只读单个 change 目录）。

**定序（推荐：它先、本变更后）**：① 它正在收口，且会删掉本变更**并不依赖**的 `build_native_client`；② 本变更要新建 ADR，编号须排在它的新 ADR 之后（D9）；③ 同文件串行可避免合并冲突里"谁是当前形态"的歧义。
⇒ **开工前必须先重读 `src/infra/llm/provider/factory.py` 的当前形态** —— 本 design 的证据 E1 可能已过时。

另：`turn-provenance-observability` 也在动 `agent_service.py` / `log_events.py` / `log_event_specs.py` / `const.py`（正是本变更 P2 / P3 的落点）⇒ 同样需定序，或开工前 rebase 确认。

**开工前置断言（可执行、含责任人；评审 I4 —— 上一版只有"重读文件"一句，无可核对条件）**

| # | 断言 | 判据 | 为什么必须 |
|---|---|---|---|
| 1 | **生产自有键与评测键无交集** | 生产侧角色超时/重试使用**自有键名**（见 D2「键名归属」），且与 `RAGAS_*` 族**无交集** | 第三轮 I6 之前，D11 曾打算"复用 `RAGAS_HTTP_TIMEOUT_*`"，而对方已定把那族键"复用 · 承载点换位" ⇒ 对方改键即**静默改生产**。改为自有键后，本条从"等对方别改"退化为**本侧可自证**的"确认无交集" |
| 2 | **`build_native_client` 去留已定** | 它已被删或明确保留，且本变更对 `build_chat` / `build_embeddings` / `build_rerank` 的改动与其无冲突 | 它是 deepeval 的删除对象，同处 `factory.py` |
| 3 | **其新 ADR 编号已落** | `docs/adr/` 的最大编号已包含它那条取代 ADR-0024 的新 ADR | 本变更的 ADR 编号须排在它之后（D9） |

**责任人**：本 change 的实施者；**三条未全部成立前 SHALL NOT 开工**（顺序约定见上，推荐"它先、本变更后"）。
