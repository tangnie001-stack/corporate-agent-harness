## Why

现有报警轮是**自由分析**：把告警文本按固定模板喂给 Agent，模型自由发挥。三个后果：

1. **结论不可复用、不可评估** —— 每次输出形态不同，无法回归、无法统计准确率。
2. **对低流量接口的固有波动给出无用解释** —— 实测（近 6 小时 90 个分钟点）：`/welife-pay/pay/createOrder` 每分钟约 **2 单**，分钟级 `avg` 在 647–695ms 波动；而告警条件是「连续 5 次评估、每次取最近 1 分钟的 `avg(upstream_response_time)`、均 > 1000ms」。这个量级下，两单同时偏慢就会触发，且该告警 1 天前刚报过、系统自动关闭。模型面对它仍会编出一个"看似合理"的原因。
3. **值班人仍需自己判断要不要处理** —— 产品价值无法落地。

本次变更是把报警轮从"自由分析"改为**证据驱动的三档判定**：先判断异常是否统计显著，再决定给不给原因。

## What Changes

- 新增 **skill 驱动的证据采集**：skill frontmatter 声明证据清单（`tool` / `params` / `required` / `timeout` / `when`），由代码解析并**分波并行**执行，不交给模型决定"查什么"。
- 新增 **告警上下文解析**：从 Grafana 规则定义（ruler API）解析出接口 URI、阈值、`for` 时长与聚合方式，补齐现有载荷缺失的可执行参数。
- 新增 **3 个只读取数能力**：`latency_stats`、`request_detail`、`business_impact`，经 Grafana 的 `/api/ds/query` 代理查询 SLS。
- 报警轮的**输入构造**由「固定模板的告警文本」改为「告警上下文 + 证据包 + skill 判定正文」。
- 报警轮的**结论形态**由自由文本改为**结构化三档**（`无需处理` / `建议观察` / `需要处理`），定量字段由代码从证据注入、模板渲染后沿用现有推送通道。
- **判定档位由代码确定**，模型只产出解释类字段（一句话结论、假设、反证、下一步、置信度），不产出档位。
- **保守判定**：`无需处理` 必须有正向证据，且需同时满足样本量与严重度条件；证据不足一律降为 `建议观察`，禁止"没找到原因 = 没问题"。
- **显式降级**：证据源三态（`ok` / `empty` / `failed`），`failed` 与 `empty` 在结论中必须分开表述；`required` 源失败只出"证据不足"。
- **能力开关**：默认关闭，按告警名白名单灰度；关闭时行为与变更前一致。

**非目标**（不在本变更内）：支付库查询（另一变更）、`sls-mcp-service` 独立服务（另一变更）、Grafana 告警规则拆分（运维侧动作）、自动静默与自动建单。

## Capabilities

### New Capabilities

- `alert-triage`: 告警上下文解析（规则反查）、证据采集（skill 声明清单、分波并行、超时与三态）、三档判定（代码定档 + 正向证据校验）、降级、卡片渲染与落库。

### Modified Capabilities

- `alert-notify`: 报警轮的输入构造由固定模板改为「告警上下文 + 证据包 + 判定正文」；结论形态由自由文本改为渲染的三档卡片；结论落库由原始输出改为渲染文本 + 结构化判定。三项都改变 spec 级行为（当前要求写死了"输入由固定模板构造"与"结论取净化正文"）。

## Impact

**代码**

- 新增 `src/rca/`：`context.py`（规则反查）、`loader.py`（skill 解析）、`collector.py`（证据采集）、`judge.py`（判定）、`render.py`（卡片渲染）
- 新增 `src/rca/sources/`：`LogSource` 协议、`GrafanaLogSource`（生产）、`FixtureLogSource`（测试）
- 修改报警分析的入口构造与结论落库/推送（现位于 `src/api/alerts.py` 及其调用的服务层）
- 新增 `skills/rca-latency/SKILL.md`（运行时内容库，随镜像发布）

**接口 / 契约**

- 对外：无新增 HTTP 接口；沿用 `/api/alerts/webhook/{token}`
- 对内：新增对 Grafana 的三处调用——ruler API（规则定义）、annotations API（告警历史）、`/api/ds/query`（日志查询代理）

**依赖**

- 无新增第三方库（Grafana 走 HTTP；不引入 SLS SDK）
- 新增一个服务账号（Viewer）与 Bearer token，随环境变量注入
- 推送渠道沿用现有企微通道

**风险**

- 三档判定可能误判 `无需处理` 而漏掉真故障 —— 以保守策略 + 严重度条件 + 误拦回访缓解（见 design）
- Grafana 的 `/api/ds/query` 返回 `status` 恒为 500（实测），客户端必须按 `frames` 判空，否则会把成功查询当失败
- 规则定义解析依赖 SQL 写法（`request_uri = '...'`），写法不一的规则会解析失败，需兜底
