## 1. 前置判断：真正的天花板是 provider 配额，不是副本数

调研结论 + ADR-0020（直连 provider，无网关）叠加后得到一个反直觉结论：

> **并发上去后第一个撞墙的是上游模型的 RPM/TPM 配额，不是 app 的 CPU。Uber 全公司 LLM 网关峰值也只有 25 QPS。**

因此：**加副本解决不了 429**。配额/闸门层是独立的一道地基，必须有，且不能靠"加机器"绕过。

## 2. 目标态架构

### 2.1 10x（几十 → 数百并发会话）：同构多副本 ＋ 状态全外置

```
                ┌─────────────── SLB（轮询，无 sticky）───────────────┐
                │                                                    │
        ┌───────▼────────┐   ┌────────────────┐   ┌────────────────┐│
        │  app 副本 #1   │   │  app 副本 #2   │   │  app 副本 #3   ││
        │  FastAPI+图    │   │  （无状态）    │   │  （无状态）    ││
        └───┬────────┬───┘   └───────┬────────┘   └───────┬────────┘│
            │        │               │                    │         │
            │        └───────────────┴────────────────────┘         │
            │                     Redis（托管）                      │
            │      · chat_lock / 预留    · abort 标志                │
            │      · 事件 Stream(可回放) · Pub/Sub 扇出              │
            │      · 租约（选主：定时任务 / 企微 bot 单活）          │
            │                                                        │
            └──────────────► RDS / PG（历史、检索、配额计数）────────┘
```

**六条状态外置映射**（今天在进程内 → 将来在 Redis）：

| 今天（进程内） | 10x 的目标位置 | 说明 |
|---|---|---|
| `_session_tasks: dict[str, asyncio.Task]` | **留在本地**，但"哪个会话在跑"要能在 Redis 查到 | Task 本身天然是本地的；关键是**别的副本要能知道/干预** |
| `_abort_signals: dict[str, asyncio.Event]` | Redis 标志 + Pub/Sub 触达 | cancel 端点可能落到任意副本 |
| `_stream_buffers`（事件缓冲，TTL 300s / MAX 2000） | Redis **Stream**（不是纯 Pub/Sub） | 重连落到别的副本要能回放；Pub/Sub 不持久会丢 |
| `_seq_counters`（每会话序号） | Redis `INCR`（全局单调） | **最容易漏的一条**：换实现后 seq 必须仍单调，否则 `after_seq` 回放错乱 |
| `task_registry`（TTL 1800s） | Redis Hash | 与事件缓冲同寿命假设 |
| `_reserved`（无 await 原子预留） | 保留为**降级路径**，权威改回 Redis SETNX | 见 §3-P0-2 |

**两条硬约束**（来自调研，逐条有出处）：
- **不要用 sticky session 代替状态外置**——它只是推迟问题，滚动发布/故障时一次性丢掉整机会话。
- **回放不能用纯 Pub/Sub**——Pub/Sub 不持久，断连数秒内的事件永久丢失；要可回放必须 Stream + `Last-Event-ID`。

**定时任务与长连接的单活**：`summary_scheduler`、Langfuse trace 保留期清理、**企微长连接**，多副本下都会 N 份并发执行或互相顶号 → 统一用 **Redis 租约选主**（与 `chat_lock` 同一原语）。

### 2.2 100x（数百 → 数千并发会话）：在 10x 之上加四件

1. **背压队列**：agent 一轮是数十秒的长任务，突发流量直接打死副本。入口用**托管 MQ**（阿里云 RocketMQ / MNS）削峰，队列深度作为扩缩容指标。
2. **配额与闸门层**：token 感知的 RPM/TPM/并发配额（按 user/team），超限返 429 + `retry-after`；外加**全局 LLM 并发闸门**保护 provider 配额。调研明确：用 RPS 限流 token 型负载是错的。
3. **数据面分离**：
   - 检索读 → RDS 只读副本 + 连接池（pgvector 仍是单点；**只有它真成瓶颈**才引入专用向量库——属于允许的"现成组件"）
   - 历史写 → 每轮写 PG 在高并发下是热点，改异步/批量
   - **语义缓存**：企业内部问题重复率高，是这里收益最大的一项
4. **观测与成本**：Langfuse 采样率下调（trace 写自身会成热点）+ 成本归因到 team/case。

### 2.3 扩展手段对照

| 层面 | 10x 的手段 | 100x 再加 |
|---|---|---|
| 计算 | app 副本 ×2~4，无状态 | 自动扩缩容（按队列深度） |
| 会话/任务态 | Redis | 同左（加 TTL/容量治理） |
| 流式 | Redis Stream + Pub/Sub 扇出 | 同左（加采样/合并，降 SSE 帧频） |
| 定时/长连接 | Redis 租约单活 | 独立"连接持有者"进程 |
| 数据 | RDS（可先不动） | 只读副本 + 连接池 + 写异步化 |
| 模型调用 | 全局并发闸门（空转也要先埋） | 多维配额 + 路由/降级 |
| 成本/质量 | — | 语义缓存 + 采样 + 归因 |

## 3. 当前要埋的地基

排序依据：**"现在不做，将来要重写而不是换实现"** 的代价。

### P0 — 接口隔离（行为完全不变，代价低）

1. **把 `streaming_manager` 拆成 4 个接口 + 进程内实现**
   `SessionRunStore`（谁在跑/预留）、`AbortChannel`、`EventLog`（缓冲 + seq）、`EventSink`（订阅/回放）。
   今天实现照旧，将来换 Redis 实现只改**一处装配点**。
   - **关键子项：seq 生成器必须独立成组件**（现在是 `_seq_counters` 进程内自增；换实现时最容易漏的就是这条）。

2. **把并发闸门收敛为单一抽象 `ConcurrencyGate`，并写明「Redis 权威 / 进程内降级」的契约**
   现状是两层但关系隐含：`chat_lock`(Redis, `src/services/chat_lock.py`) 为权威，`_reserved`(进程内无 await 预判, `src/chat/task_registry`同文件族) 为 Redis 不可用时的兜底。**把这条关系写成契约**，否则多副本时会出现"两层都以为对方兜住了"。

3. **引入 Redis 租约（lease）基础件，并先修一处现存隐患**
   `src/main.py::_clear_stale_chat_locks` 目前 `redis.keys("chat_lock:*")` + 全量 `delete`：
   - 单副本安全（启动时确实没有在途任务）；
   - **多副本下，一个副本启动会删掉其他副本正在持有的锁** → 同会话可并发进入。→ 必须改为"只清自己的"（或按 owner 标记清理）。
   同一件基础件顺带包住 `summary_lock` / `summary_scheduler` / 将来的企微单活。

4. **企微长连接的所有权显式化**
   现状 `wecom_service.start()` 在 lifespan 直接连（`src/main.py`）。多副本下 N 个进程连同一批 bot → 互相顶号（代码已把 `event.disconnected_event` 处理成"主动断开不抢回"，等于靠抖动维持事实单活）。
   地基 = 把"谁持有 bot 连接"交给 Redis 租约决定；今天单副本恒得，将来相互竞争有确定语义。

### P1 — 契约补齐（为多副本的正确性铺路）

5. **请求幂等键**：`POST /api/chat/stream` 目前只有 trace_id。SLB 重试或副本滚动时可能重复执行同一轮 → 加 idempotency key 是**正确性**前提，不只是优化。
6. **优雅停机语义**：uvicorn 已有 `--timeout-graceful-shutdown 30`，缺的是"**停止接新流 ＋ 在途轮显式收尾**"的语义（现状靠 30s 超时兜底）。**今天就在做滚动发布**，所以这条今天就该有。
7. **LLM 调用统一入口预留闸门挂点**（先空实现 + 计数埋点），将来配额层直接插，不动业务代码。
8. **配置/端口不写死**：compose 名与端口散落写死是多副本/多环境的前提性障碍。

### 明确现在**不做**

托管 MQ、独立 worker 池、K8s / 服务网格、语义缓存、专用向量库、独立 LLM 网关 —— 这些是 **100x 的产物**，等 §4 的触发条件成立再上。现在上属于过度设计。

## 4. 触发条件表（"什么时候做哪一步"）

| 观察到的信号 | 结论 | 动作 |
|---|---|---|
| 单副本 CPU/内存持续 >70%，或 SSE 连接数接近单机上限 | 该上多副本 | **10x**：加副本 + 状态外置（P0 已就位 ⇒ 只是换实现 + 改副本数） |
| 出现 **429 / retry-after**，或 provider 配额打满 | **加副本无用** | 配额层 + 全局 LLM 并发闸门（100x 第 2 项） |
| 首字延迟 P95 恶化 / 请求排队 | 该削峰 | 托管 MQ 背压 + 以队列深度扩缩容（100x 第 1 项） |
| RDS CPU 打满、检索 P95 恶化 | 该扩读 | 只读副本 + 连接池（100x 第 3 项） |
| 企微 bot 出现被顶号抖动 / 时而回话时而不回 | 单活没做好 | 租约单活（P0-4） |
| 滚动发布时在途轮报错或用户看到"正在思考"卡死 | drain 缺失 | 优雅停机语义（P1-6） |
| 下游要求多副本但取消/重连行为错乱 | 状态外置未做 | 回到 P0-1 |

## 5. 不确定点 / 待定

1. **生产是否已经跑 2 台机？** runbook §待定项写「单机自建」，而更早的容量记录写「可部署 2 台机」。若已有多副本，则 §3-P0-3 的 `_clear_stale_chat_locks` **今天就在误删锁**。→ 需用户确认。
2. **SIGTERM 后在途轮的落库终态**是 `complete` 还是 `interrupted`？未核（与既有"空回答却置 complete"缺陷相关）。
3. **千级文档下 pgvector 是否真的需要读副本**：未测——读扩展的收益可能很小（文档量不变）。
4. **Langfuse 自身在高并发下是否成为写热点**：未测。
5. 语义缓存的命中率在本域（企业内部财务问答）**未标定**，收益不能照搬 30–70% 的通用区间。
